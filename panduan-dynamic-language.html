Skenario A — Manual Multi-Language Database
File: database/schema-i18n.sql + api/articles-i18n.js

A1. Arsitektur Tabel Database

Desain menggunakan tabel terpisah (article_translations), bukan kolom tambahan di tabel articles. Ini keputusan arsitektur penting — alasannya:

  • Mudah menambah bahasa baru: tambah baris saja, tidak perlu ALTER TABLE
  • Tabel articles tetap bersih: tidak ada 20+ kolom bahasa yang mengacaukan schema
  • Partial translation OK: artikel boleh hanya ada terjemahan EN tanpa ZH
  • Audit siapa yang menerjemahkan: ada kolom created_by dan reviewed_by

Diagram Relasi Tabel

articles (tabel asli — schema.sql)
  │  id, title, content, excerpt, status, ...
  │
  └── article_translations  (1 baris per artikel per bahasa)
        id
        article_id  → articles.id  (CASCADE DELETE)
        lang_code   → 'id' | 'en' | 'zh' | 'ar' | ...
        title       → judul dalam bahasa ini
        content     → isi HTML dalam bahasa ini
        excerpt     → ringkasan dalam bahasa ini
        source      → 'manual' | 'ai_cache' | 'machine'
        review_status → 'pending' | 'approved' | 'rejected'
        created_by  → users.id (siapa yang menulis terjemahan)
        reviewed_by → users.id (siapa yang menyetujui)

  CONSTRAINT: UNIQUE (article_id, lang_code)
  → Satu artikel, satu bahasa = satu baris saja

Fungsi PostgreSQL: fn_article_with_lang()

Fungsi ini menangani fallback secara otomatis di level database — jika terjemahan belum ada, kembalikan konten asli tanpa error.

-- Cara pakai di backend Node.js:
const result = await db.query(
  'SELECT * FROM fn_article_with_lang($1, $2)',
  ['art-001', 'en']
);
// result.rows[0].is_fallback → true jika tidak ada terjemahan EN
// result.rows[0].lang_served → 'id' jika fallback, 'en' jika ada

A2. Alur Language Detection di API

GET /api/v1/articles/art-001?lang=en
1
detectLanguage(req) — cek 3 sumber: query param ?lang, header X-App-Language, browser Accept-Language
↓
2
Validasi UUID — tolak jika format ID artikel tidak valid
↓
3
Query fn_article_with_lang(id, 'en') — database mencari terjemahan approved
↓ dua kemungkinan
4
Terjemahan ada → kembalikan konten EN, is_fallback=false, lang_served='en'
4
Terjemahan tidak ada → fallback ke konten ID, is_fallback=true, lang_served='id'
↓
5
Set HTTP Headers: X-Lang-Served, X-Lang-Fallback, X-Lang-Requested → frontend bisa tampilkan banner "terjemahan belum tersedia"

Urutan Prioritas Deteksi Bahasa

// Sumber 1 (tertinggi): query param eksplisit dari user
GET /api/v1/articles?lang=en

// Sumber 2: header custom dari lang.js frontend
X-App-Language: en

// Sumber 3: browser setting otomatis
Accept-Language: en-US,en;q=0.9,id;q=0.8

// Sumber 4 (fallback final): default 'id'

Cara Frontend Kirim Bahasa ke Backend

// assets/js/lang.js sudah menyimpan pilihan di localStorage
const lang = localStorage.getItem('rm_lang') || 'id';

fetch(`/api/v1/articles/art-001?lang=${lang}`, {
  headers: {
    'X-App-Language': lang,  // backup, jika query param tidak terbaca
  }
})
.then(r => r.json())
.then(json => {
  const { data } = json;
  document.querySelector('#title').textContent  = data.title;
  document.querySelector('#content').innerHTML = data.content;

  // Tampilkan banner jika sedang fallback ke Bahasa Indonesia
  if (data.is_fallback) {
    document.querySelector('#fallback-banner').style.display = 'block';
  }
});

Skenario B — AI Translation + Smart Cache
File: api/translator.js + tabel translation_cache di schema-i18n.sql

B1. Alur Kerja Smart Cache

POST /api/v1/articles/:id/translate — { lang: "en" }
1
Ambil artikel published dan hitung hash sumber dari title + excerpt + content, lalu cari cache fresh dengan hash yang sama.
↓ dua jalur
2a
Cache HIT → kembalikan langsung, from_cache=true, tokens_used=0. 0 API call, 0 biaya.
2b
Cache MISS (stale / belum ada) → lanjut ke langkah berikut
↓ (hanya jika cache miss)
3
Jika cache miss, kirim judul, excerpt, dan konten artikel ke Gemini API.
↓
4
Kirim ke Gemini API dengan prompt terstruktur. Satu request = terjemahkan judul + excerpt + konten sekaligus.
↓
5
Parse JSON respons dari Gemini. Validasi semua field wajib ada (title, content).
↓
6
UPSERT ke translation_cache dengan cache_status='fresh', simpan token usage.
↓
7
Kembalikan ke frontend dengan from_cache=false, tokens_used=jumlah_token.

B2. Mekanisme Cache Invalidation Otomatis

Saat penulis mengupdate konten artikel, cache terjemahan lama menjadi tidak akurat. PostgreSQL trigger menangani ini secara otomatis:

-- Trigger di schema-i18n.sql (otomatis, tidak perlu kode manual)
-- Kapan trigger aktif: saat articles.title atau articles.content diupdate
-- Apa yang dilakukan: ubah cache_status dari 'fresh' → 'stale'

-- Contoh: penulis mengedit artikel art-001
UPDATE articles
   SET content = 'Konten baru...'
 WHERE id = 'art-001';

-- Trigger otomatis menjalankan ini di belakang layar:
UPDATE translation_cache
   SET cache_status = 'stale'
 WHERE article_id = 'art-001'
   AND cache_status = 'fresh';
-- → Permintaan terjemahan berikutnya akan regenerasi otomatis
source_hash adalah SHA-256 dari (title + excerpt + content) saat terjemahan dibuat. Ini dipakai sebagai verifikasi ganda — trigger PostgreSQL mengubah status ke 'stale', dan kode backend memverifikasi ulang dengan menghitung ulang hash.

B3. Prompt Engineering untuk Gemini

Kualitas terjemahan sangat bergantung pada prompt yang ditulis. Struktur prompt di api/translator.js:

const prompt = `You are a professional translator for an Indonesian cultural
editorial platform called "Racik Media".

TRANSLATION RULES:
1. Preserve the original meaning, tone, and cultural nuances.
2. Keep proper nouns (places, names, product names) in Indonesian.
3. Do NOT add commentary or explanations.
4. Output ONLY valid JSON — no markdown, no code blocks.

INPUT:
{
  "title": ${JSON.stringify(title)},
  "excerpt": ${JSON.stringify(excerpt)},
  "content": ${JSON.stringify(plainContent)}
}

OUTPUT FORMAT:
{
  "title": "translated title",
  "excerpt": "translated excerpt",
  "content": "translated content"
}`;
Mengapa konten HTML di-strip dulu? HTML yang dikirim ke AI boros token dan kadang membuat model "terganggu" oleh tag. Kirim plain-text ke AI, simpan terjemahan plain-text, lalu gunakan sebagai fallback jika HTML asli tidak dibutuhkan. Untuk konten HTML penuh, pertimbangkan kirim struktur HTML yang disederhanakan.

B4. Alur Review & Publish oleh Admin

1
User meminta terjemahan
Frontend memanggil POST /articles/art-001/translate dengan { lang: "en" }. Hasilnya disimpan di translation_cache dengan status 'fresh'.
2
Admin preview di dasbor moderasi
Admin membaca terjemahan AI. Jika bagus → langkah 3. Jika perlu perbaikan → edit manual di form, simpan ke article_translations langsung.
3
Admin meng-approve (promote)
Klik tombol "Publish Terjemahan". Frontend memanggil POST /articles/:id/translations/promote dengan { cache_id }.
4
Fungsi fn_promote_cache_to_translation() berjalan
PostgreSQL UPSERT data dari translation_cache ke article_translations dengan review_status='approved'. Cache ditandai 'promoted'.
5
Terjemahan live di halaman publik
Endpoint GET /articles/:id?lang=en sekarang mengembalikan konten English yang sudah approved. is_fallback=false.
